# 記事シリーズ計画: 「つまずき1項目 = 1記事」

方針: エラーの文言で検索する読者(=いま困っている人)を入口にする。1本ごとに深く書く。
素材: `article-draft.md`(7項目の下書き)。各記事は、そこから書き起こす。

## 構成(7項目 → 5記事 + 補足1本 + ハブ)
| # | 記事 | 素材(draft) | 検索されそうな言葉 | 厚み |
|---|---|---|---|---|
| 1 | Stripe の API キー・Webhook シークレットが入らない(401、長さで確認する) | 3-1, 3-2 | `Invalid API Key provided` | 中 |
| 2 | Stripe Checkout の 400「product tax code is missing」(Managed Payments) | 3-3 | `Managed Payments tax code` | 大 |
| 3 | 決済は通ったのにメールが来ない: Webhook が 400 を返す設計と、Stripe の再送信 | 3-4 | `Stripe webhook 400` | 大 |
| 4 | Gmail の SMTP 設定: `Name or service not known` とアプリパスワード | 3-6, 3-7 | `SMTP Name or service not known` | 中 |
| 5 | 失敗の理由が分かるログの作り方(キーの長さ、エラー本文、理由別ログ、Render のログの見方) | 3-5 ほか | `Render ログ 表示されない` | 中 |
| 6 | AI と一緒に作って分かったこと | 3-8 | — | 中 |
| ハブ | 全体像と、上の記事への一覧(最後に作る) | 骨子 1, 2, 4, 5 | — | 小 |

組み替えた理由: 3-1 と 3-2 は原因が同じ。3-5 は単独だと薄い。3-6 と 3-7 は続けて読ませたい。

## 順番とペース
- 週に1本(約6週間)。最初は #2 か #3(独自性が高く、検索で見つかりやすい)
- ハブは最後。各記事の公開後に、ハブと他記事へのリンクを足していく
- 各記事の末尾: 「手順書とスターターキットを準備中」の一文(売り込みにしない)

## 1本ごとのテンプレート
1. タイトル(エラー文言を含める)
2. 先に結論(原因と直し方を3行で)
3. 症状(実際のログ・画面。秘密は伏せる)
4. 原因の見分け方(どうやって絞ったか)
5. 直し方(手順、コード)
6. 再発防止(ログ、設定、チェック)
7. 「執筆時点(日付)の情報」の注記
8. 末尾: 準備中の一文 + シリーズの他記事へのリンク

## 公開前チェック(毎回)
- [ ] スクリーンショットに、キー・パスワード・メールアドレス・注文番号・DL URLが写っていない
- [ ] 本文に、シークレットの値(末尾の数文字も)が入っていない
- [ ] 収入・売上・「簡単に稼げる」の表現がない
- [ ] 外部サービスの仕様を書いた箇所は、公式ドキュメントで確認し、日付を入れた
- [ ] 実際のログの数字・文面と合っている
- [ ] AI アシスタントを使ったことを、隠さず書いている
- [ ] 投稿先のルール(有料誘導、宣伝の扱い)に反していない

## 反応の見方
- 1本ごとに、1週間後の閲覧数・コメントを記録する
- どの記事に反応があったかで、手順書の厚くする章を決める
- 反応が少なくても、1〜2本で結論を出さない(題材・タイトルを変えて見直す)
