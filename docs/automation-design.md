# 記事自動化ツール(articlebot)設計

目的: 「記事の執筆 → note への転記」を自動化する。**当面、人間は「プレビュー確認」と「承認」だけ行う。**

## 原則
1. **自動公開はしない。** 公開ボタンは、必ず人間が押す
2. **承認は、内容に紐づく。** 承認後に1文字でも変われば、書き出せない(sha256 で照合)
3. **事実に基づく。** この記事シリーズの価値は「実際に起きたこと」。確認していないことを、事実のように書かない(`【確認】` が残る限り、承認できない)
4. **秘密を出さない。** キー、シークレット、署名付きURL、メールアドレスは、機械的に止める
5. **規約を守る。** 投稿先の規約に反する自動化は、しない

## 全体の流れ
```
素材(実際のログ・画面・出来事) ─→ [段階2] 下書き生成 ─→ [段階1] 検査 ─→ プレビュー ─→ 承認(人間) ─→ 書き出し ─→ [段階3] note へ転記 ─→ 公開(人間)
                                                         ↑ 自動                           ↑ 人間の2つのゲート                        ↑ 要規約確認
```

## 段階1(実装済み): 検査 → プレビュー → 承認 → 書き出し
`tools/articlebot/articlebot.py`(標準ライブラリのみ。テストは `tests/test_articlebot.py`)

| コマンド | 内容 |
|---|---|
| `lint` | 秘密鍵・Webhookシークレット・署名付きDL URL・実在しうるメールアドレス・収入の約束・`【確認】`の残り・**AI利用の明記なし**を error に。表・4段以上の見出し・執筆時点の注記なしを warn に |
| `preview` | 検査結果つきの HTML を生成(スマホ幅で確認できる)。**目視確認は人間** |
| `approve --by 名前 --reviewed` | error が0で、**人間が「全文を読み、事実を確認し、必要な修正を自分で行った」と宣言(`--reviewed`)したときだけ**、承認(内容の sha256、承認者、宣言、日時)を記録 |
| `export` | 承認済み、かつ、承認後に変更がないときだけ、公開用の本文を出力(内部コメントは除去) |
| `export --html --out paste.html` | 承認済みの本文を、**note の編集画面に貼りやすいページ**にする(「タイトルをコピー」「本文をコピー」ボタン付き)。承認が通らなければ作れない |

- コメント(`<!-- -->`)は、公開時に除去される。コメント内の `【確認】` は数えないが、**秘密情報は、コメント内も検査する**
- 承認ファイル(`*.approval.json`)は、承認の記録として残す

## 段階2(未実装): 素材 → 下書き生成
- 入力: 構造化した「素材」(症状、実際のログ、原因、直し方、**確認済みかどうか**)
- 生成: Claude API で、決まった型(結論 → 症状 → 原因 → 直し方 → FAQ)に沿って下書きを作る
- 守ること:
  - 素材にないことは書かない。**確認済みでない事実は、`【確認】` を付けて出力させる**
  - 秘密の値を、プロンプトに入れない(ログは、事前にマスクする)
  - 出力は、必ず段階1の検査に通す
- 必要なもの: Claude API キー(利用料金がかかる)、素材の入力形式の決定
- 先に決めること: 素材をどうやって集めるか(手で書く / 作業ログから抽出する)

## 段階1c(実装済み): 読みやすい記事ページ(自前サイト)と、note用の見出し画像
- `preview <記事> --site` / `export <記事> --site --out store/static/articles/<slug>.html`
  - 進捗バー、スクロールで現れるセクション、重要語のマーカー、目次(スムーススクロール)、結論カード、FAQカード、コードのコピーボタン、ダーク/ライト対応、スマホ幅対応
  - 動きは補助にとどめ、「視差効果を減らす」設定では、すべて無効になる
  - `export --site` は、承認が通らなければ作れない。公開版に、検査パネルは出ない
  - 配置すると `/articles/<slug>` で配信される(`store/app.py`)。push すれば、Render が公開する
- `eyecatch <記事> [--sub 説明]`: note の見出し画像(1280x670)用の HTML を作る。ブラウザでスクリーンショットを撮って使う
  - note では、アニメーションは使えない前提。見出し画像と、文章の見せ方(短い段落、結論を先に、箇条書き)で、印象を変える

### note を先に公開し、自前サイトにリンク付きで載せる運用(決定済み)
1. note に公開する(`export --html` の貼り付け用ページで貼り、公開は人間が押す)
2. note の記事URLが決まったら、サイト用ページを作る:
   `export <記事> --site --note-url https://note.com/<ユーザー名>/n/<記事ID> [--canonical] --out store/static/articles/<スラッグ>.html`
   - ページ上部に「この記事は note でも公開しています」のリンクが入る
   - `--canonical`: 検索エンジンに、note 側を正とも伝える(重複コンテンツ対策。サイト側の記事は、検索上位を狙わない)
   - note の URL 以外(http、他ドメイン、属性の挿入など)は、受け付けない
3. 配置して push すると、`/articles/<スラッグ>` で公開される

## 段階1b(実装済み): 承認 = 実質的な投稿ボタン(貼り付け支援)
`approve` → `export --html` → ページでコピー → note の編集画面に貼る → **公開は、人間が押す**。
ツールは note の画面を操作しない。規約上の心配がなく、手作業は、数十秒〜数分。

## 段階3(未実装・要判断): note への転記の完全自動化
**注意: note には、記事を投稿する公式の API が、ないと私は認識している(未確認)。** 自動化するなら、ブラウザ操作(Playwright など)になる。
リスク:
- **note の利用規約に反する可能性**。禁止事項に「自動化されたアクセス」「ボット」が含まれていないか、事前に確認する
- アカウントの制限・停止(自動操作が、不正と判定される可能性)
- 画面の変更で壊れる(保守コスト)
- ログイン情報を、リポジトリや環境変数に置くリスク

進め方の案(規約で許される場合のみ):
1. まず、**規約・ヘルプで、自動操作の可否を確認**する。不明なら、note のサポートに問い合わせる
2. 許される場合でも、**「下書き保存」までにとどめる**。公開は、人間がnoteの画面で押す
3. ログインは、人間が手動で行ったブラウザのセッションを使う(パスワードをツールに渡さない)
4. 規約上NGなら、**段階1の書き出し(コピー用テキスト)+ 人間が貼り付ける**運用のままにする。これでも、実作業は数分

## 投稿先(note)の規約について(ユーザー確認済みの内容。**原文は未確認**)
- 「AI 100%自動生成の投稿は禁止」「AI 利用の明記が必須」と、ユーザーが規約から確認した
- 対応: 承認前に、人間が全文を読み、事実を確認し、**自分で修正・加筆する**(承認時に `--reviewed` で宣言)。AI 利用は、記事内に明記する(未記載だと承認できない)
- 未確認: 「100%」の線引き(承認だけで人間の関与と認められるか)、明記の書式の指定、**自動操作(ボット・自動投稿)の扱い**(これは別の規約)。規約の原文で確認する

## 品質・評判のリスク(自動化するときの注意)
- 検索エンジンや媒体は、**量産された低品質な記事**を、評価しない方針を取ることがある。人間の承認と、実体験に基づく素材は、その対策になる
- 記事に、AI を使ったことを明記する(検査で warn)
- 自動化で記事数を増やすより、**1本ごとの質と、反応の確認**を優先する

## 次の決定事項
1. note の規約・ヘルプで、自動投稿・自動操作の扱いを確認する(段階3の前提)
2. 素材の形式を決める(段階2)
3. Claude API を使うか(費用・キー管理)を決める
