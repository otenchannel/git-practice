# 公開〜本番化チェックリスト

現在地: **技術面は完成(テスト環境で購入→メール→DLまで確認済み)。以下を済ませると、実際に売れる状態になる。**

## A. 特定商取引法の表記(必須)
個人情報はコードに置かず、Render の Environment に追加する(追加すると自動で再デプロイ)。

| 変数 | 内容 | 例 |
|---|---|---|
| `LEGAL_SELLER` | 販売事業者(氏名または屋号) | 山田商店 |
| `LEGAL_REPRESENTATIVE` | 運営責任者 | 山田太郎 |
| `LEGAL_DISCLOSURE` | 所在地・電話番号の扱い | 請求があった場合に遅滞なく開示します |
| `LEGAL_EMAIL` | 連絡先メール | support@example.com |

- 確認: `https://<サービスURL>/legal` に【未設定】や管理者向け警告が出ていなければOK
- 所在地・電話番号を省略(請求時開示)できる条件には要件がある。**消費者庁の最新ガイドラインか専門家に確認**すること
- 本番キー(`sk_live_`)を設定すると、上記が未設定の場合は **起動を拒否**する(安全装置)

## B. 商品を本物にする
1. `store/products/` に商品ファイルを置く(PDF/ZIPなど)
2. `store/products.json` の `name` / `description` / `price_jpy` / `file` を更新
3. 商品ファイルはリポジトリにコミットされる。**リポジトリが公開(public)なら商品が丸見えになる**ので、privateにするか、商品ファイルは別の保管場所(例: Cloudflare R2 / S3 の署名付きURL)に移す
4. push → Render が自動デプロイ(されなければ Manual Deploy)

## C. メール送信の見直し
- 今は個人のGmail(アプリパスワード)。件数が増える/信頼性を上げるなら、独自ドメインの送信元 + メール配信サービス(SMTP対応のもの)へ。SPF/DKIM設定を行う
- Gmailには1日の送信上限がある。上限に達するとメールが失敗し、Stripeの再送で後から届く(その間顧客を待たせる)

## D. Stripe 本番切替(最後に1回)
1. Stripeで本番利用の申請(事業者情報・銀行口座・本人確認)を完了
2. 本番モードで API キー(`sk_live_...`)と Webhook(同じURL・同じ2イベント)を作成
3. Render の `STRIPE_SECRET_KEY` と `STRIPE_WEBHOOK_SECRET` を本番の値に更新(**コピー時は「表示」してから全体をコピー**。起動ログの `stripe key: length=` で長さを確認)
4. **自分で少額購入→メール→DL→(Stripeで)返金**まで通しで確認
5. Managed Payments は現在オフ(自分が販売者)。税の扱い(インボイス登録の要否・消費税)は税理士/税務署に確認

## E. 運用
- 売上確認: Stripeダッシュボード
- 失敗検知: Render の Logs で `mail failed` / `stripe webhook rejected` / `fulfill failed` を検索
- 返金・問い合わせ: メール返信 + Stripeで返金
- 費用: Render Starter(有料)+Stripe手数料(決済ごと)。使わない間は停止/削除を検討
- 税務: 売上の記録、確定申告(副収入の扱いは税務署/税理士に確認)

## F. 集客(売れるかどうかを決める部分)
仕組みは売れる場を用意するだけ。売上は商品と集客で決まる。
1. **1商品に絞って、悩みと対象を一文で言えるようにする**(誰の、どんな問題を、どう解決するか)
2. 無料で出せる入口: 悩みに答えるブログ/note記事、X(旧Twitter)やInstagramの定期投稿、YouTube/Shorts
3. 記事・投稿の末尾から販売ページ(`/`)へ誘導。販売ページの見出し・説明文は商品に合わせて書き直す(`store/static/index.html`)
4. 最初の10人は直接の知り合い・SNSで声をかけて買ってもらい、感想をもらう → 販売ページに載せる(許可を得て)
5. 数字を見る: 閲覧数 → 購入数。どこで離脱しているかで直す場所が決まる
